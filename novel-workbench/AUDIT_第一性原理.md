# 工具链审计：从第一性原理重看 novel-workbench

> 触发点：跑了 5 章，每章我都要**人工介入**。每一次介入都不是"我多事"，
> 而是工具链上有一个**能发现、却不会修**的缺口。这份文档只谈工具，不谈小说。

---

## 零、第一性原理：这套工具到底在干什么

剥掉所有节点名、闸门号、prompt 模板，这个系统只有三个动作：

```
检测(产出的形态对不对)  →  修复(把它改对)  →  记账(记住改了什么)
```

任何一个「检测到了却要人来修」的地方，都是**修复层缺失**。
任何一个「修了却没记账」的地方，都是**记账层缺失**。

实测 5 章，人工介入共 **14 次**。逐条归因后只有 3 类：

| 类别 | 次数 | 本质 |
|---|---|---|
| A. 机械可判、改法唯一，但修复器没实现 | 6 | 修复层缺函数 |
| B. 机械可判、改法不唯一，但可**有限枚举** | 4 | 修复层缺"候选+择优" |
| C. 检测本身缺失（指标测不出来） | 2 | 检测层缺指标 |
| D. 跨层冲突（两个检查互相打架） | 2 | 规则层不一致 |

**A+B 共 10 次 = 71%**，全部可以在**不调用任何 LLM** 的前提下消除。
这就是本次要修的东西。

---

## 一、A 类：改法唯一，该有函数却没有

这些问题的特征是：**正则可判、改法唯一、改完必然更对**。
让 LLM 去改它们，等于用大炮打蚊子，而且实测 N14 还会漏。

| # | 症状 | 我手工做了什么 | 该有的函数 |
|---|---|---|---|
| A1 | 破折号「——」被标 blocking，但修复器明确**不做**（注释写着"按功能改写，交给 N14"） | 逐条人工判断是打断/拖长音/插入，分别改成动作、短句、逗号 | `fix_em_dash()`：按上下文三分支机械改写 |
| A2 | 省略号「……」同理 | 手工改逗号/句号 | 已有（`want_ellipsis`），但**只在闸门报 ellipsis 子类型时触发**，第 5 章那处没被触发 |
| A3 | 「不是X是Y」/「是X不是Y」对比句式 blocking | 逐条重写 | `fix_not_is()`：删否定铺垫，直接留后项 |
| A4 | 「声音不大/不高……却/但」音量反差腔 blocking | 逐条重写 | `fix_volume_contrast()`：删音量修饰，留现场效果 |
| A5 | 单章正文出现**两个文件**（我误存草稿），通配符证据直接卡死 | 手工删草稿 | `ensure_single_body()`：写正文前/预检时校验并报出**具体文件名** |
| A6 | 字数超上限（3289 vs 2600） | 手工裁 700 字 | `trim_to_band()`：按段落信息密度排序删段（**不删剧情**） |

> A1/A3/A4 是同一个模式的三个实例：**闸门能精确指出行号和列号，修复器却不碰**。
> 这不是能力问题，是 `mechanical_fix()` 的 `want_*` 触发条件只覆盖了标点。

## 二、B 类：改法不唯一，但可有限枚举

这类不能靠单条正则，但**候选集是封闭的**，可以生成候选 + 用确定性规则择优，
仍然不需要 LLM 判断"写得好不好"。

| # | 症状 | 枚举策略 |
|---|---|---|
| B1 | 因果词复读（「果然」×44，占全部因果词 98%） | 候选集 = 18 个签约样本里出现过的因果词；规则 = 按位置轮换 + 同词 ≤3 次；**保义改法**：删词/换词/改动作后果，三选一按上下文定 |
| B2 | 微动作复读（「了一下」×9） | 候选集 = {删掉补语, 换成具体动作, 合并到前句}；规则 = 密度阈值触发，超阈值才改 |
| B3 | 过度精炼短段（59% 段落 ≤15 字） | 规则 = 相邻短段合并 + 补结构虚词；**不新增信息**，只补连接 |
| B4 | 字数不足（1626 vs 2000） | 规则 = 找"该显未显"的位置（缺因果/缺后果/缺细节判断），按缺口类型给补写指令；**不是加形容词** |

> B 类的关键是：**不改语义，只改形态**。所以可以用"枚举 + 打分"代替 LLM。
> 打分函数用可测指标（因果密度、段长分布、词频上限），不用主观判断。

**A1/A3/A4 的实测踩坑**（都是夹具自己抓出来的，不是我事后想到的）：

1. 首版 `不是A，是B` → `B`，产物是 **「这愤怒」**——系词「是」被吃掉。改为保留系词。
2. 首版 `声音不大，却…` 整段删掉，产物 **「屋里的让所有人都停了手」**——主语残缺。
   改为捕获并保留主语。
3. 我的**测试期望值本身写错了两次**（把病句当期望值），掩盖了上述缺陷。
   直到加了「主语残缺特征串检查」（`的让/的走/，这愤怒`）才暴露。

### A6 字数裁剪器的三版教训

| 版本 | 缺陷 | 后果 |
|---|---|---|
| v1 | 打分含 `- len(para)//60` 长度惩罚 | 11 字的「抚恤金」段被判低价值删掉，20 个重复动作段全留 |
| v2 | 补了信息信号，但把「门/响/空气」也算正向 | 纯环境段拿 9 分，**无一低于阈值**，裁剪器完全不动作（3475 字原样返回） |
| v3 | 氛围词改**扣分**（-3/次），正向只留对话/数字/因果/信息/强动作 | 纯环境 -45、动作 5、对话 6、信息 10；3475→2547 正确进带 |

**v2 的教训最重要**：我加信号时只想着「别删信息」，忘了「也得让环境段能被识别」。
一个只防误删、不防不删的打分器，等于没有打分器。

### C2 的真相：不是检测器缺陷，是**细纲膨胀**

我原以为 C2 是「检测器把锚句也算进照搬」。查完源码发现**工具早就支持锚句免报**
（`check-outline-copy.js` 有 `extractAnchors()`，读细纲「复沓锚句」字段逐条豁免）。
那 6 处重合确实不在锚句列表里——**检测器报得对**。

于是去量真实数据，发现了本轮最重要的东西：

| 章 | 细纲字节 | 正文可见字 | 照搬字数 | 照搬率 |
|---|---|---|---|---|
| 1 | 2,378 | 2,438 | 0 | 0.0% |
| 2 | 13,691 | 2,593 | 32 | 1.5% |
| 3 | 15,286 | 2,332 | 17 | 0.9% |
| 4 | **20,540** | 2,155 | **160** | **8.6%** |
| 5 | **22,235** | 2,282 | **131** | **6.9%** |

**皮尔逊相关系数 r = 0.814**（细纲体量 vs 照搬率）。

结论：**照搬不是 writer 的毛病，是细纲膨胀的必然结果。**
细纲写到 22KB（正文的 9.7 倍），writer 面前摆着一篇比成品还长的散文稿，
它当然会抄。而合同此前对细纲体量**没有任何上限**。

**修法**（不是让 writer 别抄，是让细纲不该被抄）：
- `check-outline-contract.js` 新增 `outline.size-budget`：细纲字节 ≤ 字数目标 × 8
- 阈值**按数据标定**，不是拍脑袋：断点落在 15,286（≤1.5%）与 20,540（≥6.9%）之间，
  取中点 ≈17,900，按 2200 字折算 ≈8.1，取整 8
- 因为**样本只有 5 章**，本项只作 advisory 不阻断；攒够章节后再回看是否收紧
- N09 提示词写入体量硬规矩 + 数据依据，从源头防膨胀

**验证**：1/2/3/6 章合规（照搬低），4/5 章超标（照搬高）——与实测照搬率完全对齐。

| 环节 | 工具行为 | 人工介入 |
|---|---|---|
| writer 交稿 | 正文 2553 字，细纲范围是 2000-2400 | 无 |
| `done C6.N12` 第 1 次 | `tracking_incomplete`：`character_snapshots` 空 | 无（守卫拦住） |
| 我把错误转给 writer | writer 自己补齐 3 人快照、自己压到 2398 字 | 无 |
| `done C6.N12` 第 2 次 | `text_preflight_failed`：`LENGTH_OVER` 2430 > 2400 | 无（预检拦住） |
| `done C6.N12` 第 3 次 | **预检自动裁到 2371，放行** | 无 |
| N13 → N15 → N16 | 全部通过，judge pass（removable 33%/0%/25%） | 无 |

**这一轮暴露并当场修掉的工具缺陷**：

修法：预检改为**读本章细纲的「字数范围」**，缺省才退回常量；N12 提示词同步说明
「上限以细纲范围为准」。

### 顺带查出的两个真缺陷

**D4 `追踪/上下文.md` 被 writer 覆写（严重）**

N11 生成的 `追踪/上下文.md` 是 S1–S7 七栏，writer 在 N12 只读它。
实测第 6 章的 writer 交稿时把该文件**整个覆写**成了另一种结构
（「写作连续性上下文 / 当前位置 / 活跃伏笔 / 近三章速记…」七栏），
全仓库搜不到这个标题——是 subagent 自己编的。

后果：下一章的 writer 会读到**缺 S2 上一章锚点、缺 S5 文风锚、缺 S7 事务说明**
的坏文件，而这三栏正是「无缝衔接」与「事务怎么填」的唯一来源。

修法：`commands._context_md_intact()`，N12/N14 交稿时校验 S1–S7 齐全。
**首版把「文件不存在」也判失败，误伤了 N14 与既有夹具**（`test_n14_done_rechecks_n13`
直接挂）——已改为「不存在→放行」，本守卫只管「存在但被改写」。

**D5 到期伏笔没有标记为「本章必办」**

上下文里 F005/F008 写着「第6章」，但 writer 看到时第 6 章正在写，
无法判断这是「本章到期」还是「已经过了」。结果两条伏笔计划回收章都是 6、
第 6 章封板后仍未回收，N19 只给 advisory 不阻断。

这是**真内容缺陷**：伏笔逾期没有任何机制拦住。

## 十一、subagent 死亡会让状态机永久卡死（2026-11-17）

第 8 章细纲的 subagent（agent-37）**中途死亡，磁盘上什么都没有**。
状态机的反应是：节点停在 `running` + 持有 token，于是 `next` 一直回：

```
{"error": "node_running", "node": "C8.N09", "hint": "先调 done 完成当前节点"}
```

**但没有任何人会再调 done**——那个 subagent 已经死了。编排者只能靠猜去调
`resume --force`。这是第 22、26、28 个 subagent 死亡累积成的同一个坑。

### 三个修复

| # | 缺陷 | 修法 |
|---|---|---|
| D6 | `max_attempts` 只是**输出给编排者看的一个数字**，没有任何代码消费它 | `next` 在发放令牌前检查 `attempts >= max_attempts` → 报 `node_exhausted`，把「该人工介入」变成机器可判的事实 |
| D7 | 僵死节点让 `next` 永远短路在 `node_running`，提示语**指向一个永远不会发生的动作** | 加僵死检测：节点 running 超 `WB_NODE_STALE_SECONDS`（默认 1800）→ 报 `node_stale`，给出「确认磁盘无产出 → `resume --force`」的可执行提示 |
| D8 | `--scope` 不认节点级 `C{n}.Nxx`，僵死恢复无法只重置一个节点的预算 | 扩展作用域语法为 `C{n}` 与 `C{n}.N{xx}`；节点级额外清掉该节点的 `attempts` |

### 实测

```
造一个 1 小时前 started 的 running 节点 → next 报 node_stale（running_seconds 7421 / 阈值 1800）
真实僵死节点 C8.N09 → resume --force --reset-budget --scope C8.N09 → 精确恢复到 C8.N09
```

**这三项的价值不在于「跑得更快」，而在于把死锁变成可诊断的状态。**
在此之前，subagent 死亡 = 流程静默卡死，编排者只能凭经验猜命令。

### D9 N09 提示词缺前序上下文 → subagent 反复死亡

第 8 章细纲的 subagent **连死两次**（agent-37、agent-38），磁盘上什么都没有。
对比发现规律：**成功的第 4/5/7 章，都是我在提示词里手写了详细前序章节摘要**；
失败的第 8 章，我给的摘要很简略。

也就是说：**这份上下文本该由工具提供，此前一直靠编排者手工补**。
N09 提示词只让 writer 去读目录/卷纲/角色表，没给前情——
writer 只能自己翻正文文件对齐，而翻文件又吃轮次又容易半途死掉。

修法：`pipeline_spec._prev_chapter_digest()` 从 `追踪/_tracking-state.json` 生成紧凑摘要：
- 最近 3 章的封板字数
- **未回收伏笔**（含计划回收章）——writer 一眼看出哪些到期了
- **角色当前状态**（身份/位置/近况）——否则 writer 不知道「陆明现在是什么身份、陆建国停职了没有」就会写偏

不读正文，避免撑爆上下文。实测注入后提示词从 1019 → 1582 字符，
agent-39 一次成功（14306 字节细纲，0 advisory）。

**顺带暴露**：账本顶层键名是 `characters`，不是 `character_snapshots`

## 十三、delta 字节上限：让人回来改是浪费（2026-11-17）

第 8 章的 tracking 事务写完后是 **3087 字节**，上限 3072——**差 15 字节**，
内容本身完全合格，却因为这 15 字节被打回，让 writer 回去再改一轮。

writer 估算字节数不准是常态（中文 UTF-8 每字 3 字节、JSON 转义、缩进都影响）。
让人回去猜「再删几个字」纯属浪费。

修法：`commands._shrink_delta_to_fit()`——超限时**自动截断长度类字段**
（summary / objective_fact / reader_knowledge / change / result / constraints /
next_chapter_commitments），**不碰** id / status / 枚举 / 必填结构，
压到刚好过线后写回文件。

实测：3087 → 3063 字节，枚举完好，守卫放行。

**首版把 `from commands import` 写成了 `from commands import _shrink_delta_to_fit`
但函数定义在守卫之前**——Python 运行时才报错，夹具立刻抓到。

## 十四、账本会骗人：截断伪装成原文 + 封板后偷改（2026-11-17）

agent-41 报了一句话让我警觉：「the committed ledger contains **truncated strings ending in "…"**」。
查下去发现两个同源的缺陷：

### 缺陷 A：截断伪装成原文

封板前的自动规整（`inline_runner._normalize_tracking`）用**固定长度**截断字段
（objective_fact→42 字、summary→32 字、next_chapter_commitments→26 字……），
而且**加「…」后缀**。问题有两层：

1. 42 字对一句中文事件描述是毁灭性的——实测账本里 E002–E005 的 objective_fact
   全被截成半句（「...，三号…」），信息**永久丢失**。
2. 「…」被 storyctl 当成**原文**写进账本，此后每次读账本都以为那是原文的一部分
   ——**截断伪装成了原始内容**。

而且它压的 key（`description`/`note`/`detail`）在 schema 里**多半不存在**，
真正的长字段 `summary` 根本没被压到。

修法：统一用 `inline_runner.shrink_delta_to_fit()`——按比例缩到刚好进限、
**不加省略号**、只截描述性字段、不碰 id/status/枚举/必填结构。
`commands._shrink_delta_to_fit()` 改为**复用**它（此前两边各有一份、规则不同，
是「同一约束两处实现」的典型坑）。

**历史遗留的修复**：走正规 revision 路径逐章重提（第 2/3/4/5 章），
`tracking_commit.py draft` → 补全被截字段 → `storyctl.py chapter commit`。
**没有直接改 state.json**（那是铁律禁止的）。

### 缺陷 B：封板后偷改正文，账本不跟随

实测第 8 章：N16 封板后有人又给正文补了因果收尾词（2383 字），
账本仍记 2348 字、sha 也不同。**sha256 此前只记录不比对**（源码注释里写得很清楚：
「曾声称"与 state 一致"，未实现，已从声称中删除」）。

后果不只是字数对不上——**伏笔回收率、文风漂移、字数统计全部基于错位的基线**，
而且没有任何机制会告诉任何人。

修法：`commands._body_post_commit_drift()` 比对「已 done 的 C{n}.N12 节点记录的
sha256」与磁盘现状，不一致就在 `done` 入口报 `post_commit_drift`。

### 顺带加了两个可见性入口

- `autopilot.py status` 增加 `ledger_truncated` 字段（列出所有被截断的路径）
- `autopilot.py ledger-repair` 子命令：报出截断项并给出修复路径

### 最终状态

```
账本截断项: 0
逐章核对（磁盘 vs 账本，8 章）: 字数全对、sha 全对、不一致 0 章
```

## 十六、一个还没解决的问题：writer 的静默死亡率

本会话里 subagent **静默死亡**（无回执、磁盘无产出）已发生 4 次：

- `node_exhausted`：attempts 达上限 → 报「该人工介入」

但**检测到僵死 ≠ 避免僵死**。每次僵死都要：
1. 人工发现（靠轮询磁盘）
2. 人工 `resume --force --reset-budget --scope C{n}.N{xx}`
3. 重新派发（提示词得重写，因为原提示词已消耗一次预算）

**从第一性原理看，subagent 死亡的主因不是模型能力，是任务粒度**：
- 写细纲 15–25 KB：agent-39 一次成功（14.3 KB），但 agent-37/38 连死两次
- 写正文 2000–2400 字：agent-33/36/41 成功，agent-26/40/44 死亡
- 死亡点几乎都在**长输出的中段**

所以「任务粒度」是可控变量：**把一次任务拆成两次，比赌一次成功更可靠**。
N12 已经用「分段 append」缓解了正文；N09 还没有对应机制。

**待验证的方案**（下一轮做）：N09 的 writer 若第一次没落盘，第二次派发时

剩下的交给断点续写器（`_partial_body_digest` 已就位）。

这比「整章一次写完」更符合 subagent 的实际承载力。

## 二十一、一次并发提交的实测（2026-11-17 14:56）

最终验收后，先前被我判定僵死的 agent-45 **又活了过来**，并跑了一次
`storyctl chapter commit --mode revision`（state_revision 14→15）。

这是一次**未经协调的并发写入**，正好检验账本一致性机制：

```
state.json     20976 字 / 9 章 / cursor=__done__
账本           revision 15 / last_committed=9 / 合计 20976 字
账本截断       0 处
封板后漂移     0 处
第9章 sha      磁盘 b32caacc… = 账本 b32caacc…
全文.md        20976 字，9 章全含
逐章记录       9 个文件，第9章 896B 无截断
next           {"done": true, "chapters_committed": 9, "words_total": 20976}
```

**结果：全部一致，没有破坏。**

## 二十二、压缩器的真 bug：result 被砍成 4 个字（2026-11-18）

agent-41 独立报告「delta.result 被截成 52 字 +「…」」。我复现后发现更严重：

```python
cut = max(4, len(val) - over - 8)
```

`over`（超出的字节数）大于字段长度时，`len(val) - over - 8` **下溢成负数**，
`max(4, ...)` 取 4 → 一句 60 字的结果说明被砍成 **「陆明用爹」** 四个字，
然后原样写进账本与 `追踪/上下文.md` 的近三章速记里。

**这不是截断，是信息摧毁，而且伪装成了原始内容。**

修法：每个字段有保底长度（result ≥24 字、summary/objective_fact ≥16 字…），
砍到保底就**换砍下一个字段**；全部到保底则返回 None（交上层报明确错误），
而不是继续砍。夹具 `test_shrink_delta_floor.py` 5 项。

**二次伤害**：修完后 `tracking_commit draft` 生成的第 5 章事务，
其 `result` 仍是旧账本里的截断值——**脏数据会从账本传播到新草稿**。
必须靠 revision 逐章重提才能清掉。实测第 3 章的历史截断也是这样清的。

## 二十九、新增检测器：相对日互斥（2026-11-18）

agent-51 挖出的 7 处日期矛盾**全是可计算的**——不需要文学判断，

1. 抽出相对日词（昨天/前天/大前天/三天前/半个月前/半年前/N年前…）及其上下文
2. 比对**相隔 ≥2 章**的同词共现，且上下文共享主题词（工亡/抚恤/停职/落款/报告/封条/鉴定/签字…）

### 检测器自己的 bug：LCS 报出根本不存在的片段

跨章重复检测首版用「二分 + `in`」求最长公共子串。实测它把第1↔2章的重复报成：

- 「精度件用四号旧床配刀**粗车**」→「配刀**精车**」

月产 7200 保留：7200÷26 ≈ 277 件/天（三车间全车间日均），
与第 9 章单台一号床子 36–52 件/天不冲突。

**这才是 agent-52 说的「回到因果链」**——不是把数换成另一个数，
而是把两个数**放回各自的口径**。

## 三十七、冷启动验收：新书开箱即具备检测能力（2026-11-19）

「确保 tools 可以完成目标」的最后一环：**工具必须能在一本没被调试过的书上跑通**。

### 冷启动实测发现的两个真 bug

**Bug 1：新书的检测能力全部静默失效。**

四轮红队挖出的「日期网断裂」（8+ 项）可自动检出——但前提是书里有
`追踪/时间线/日链.md` 与 `追踪/复沓锚句.md`。**这两样此前只在被调试过的书里
手工长出来**。冷启动实测：给一本只有正文的新书跑检测，
「日链一致性」**静默返回 0 条**——既不报也不提示，看起来「全部通过」，
实际是**根本没检**。

这是最危险的一类失效：**检测器说没问题，因为它压根没跑。**

修法：
- `autopilot.py init` 生成两个骨架模板（`_scaffold_book_files`）
- 缺基准文件时检测器**明确报出**，不再静默
- 夹具 `test_coldstart.py` 5 项：init 生成骨架 / 模板含填写说明 /
  已存在文件不被覆盖 / 缺基准明确报出 / 真实书不被覆盖

**Bug 2：IndexError 被 except 吞掉，掩盖真正的错误。**

`except Exception: return []` 把所有异常都变成「无问题」。
实测症状是「日链校验未能执行：IndexError: 5」——真实原因是
`here.parents[5]` 越界（`F:\` 盘 `parents` 长度 5、合法索引 0–4）。

```
首版  for up in range(1, 6)              → parents[5] 越界
次版  for up in range(1, len(parents)+1)  → 仍越界（+1 多余）
正解  for up in range(1, len(parents))    → 合法
```

**教训：`except Exception` 不该把「工具坏了」和「没有发现问题」混为一谈。**
现在分三类明确返回：`daychain-no-tool`（找不到工具）、
`daychain-error`（执行异常，带异常类型与消息）、`daychain-mismatch`（真的不一致）。
**绝不再有静默的 `return []`。**

## 三十九、两个检查器互相矛盾：假 BLOCK 会挡住合法投稿（2026-11-19）

同一套工具里的两个检查器，对**同一份稿子**给出了相反结论：

```
体检报告.md       → 正文 20903 字，结论「可投」
qimao_check.py    → ✗ BLOCK Q01-wordcount（纯汉字 17822 < 20000）
```

用户无法判断信谁。**一个会挡住合法投稿的工具，比没有工具更坏**——它让人
去改一份本来就够长的稿子，或者让人以为稿子不合格。

### 根因：Q01 用了平台不用的口径

`qimao_check.py` 第 174–177 行原本写着：

> 按 char-count-caliber.md 的原则：旧键不改语义，双口径并列，
> **判定仍按纯汉字（保持历史可比）**，但把平台口径同时写出来供人核对。

「保持历史可比」在**测量**上是对的，在**判定**上是错的。因为：

- 平台 `api_words` **实测与「去空白可见字符」同口径**
  （`platforms/_core/data/wordcount-caliber-finding-2026-11-13.md`：24 章中
  api_words 与可见字符精确相等 20 章、与纯汉字相等 **0** 章；纯汉字少约 16.6%）
- 平台原文写的是「需上传 2 万字」，**没说「2 万汉字」**

既然平台测的是可见字符，就不该拿汉字口径去 BLOCK 一份平台会收的稿子。

### 修法：分级，而不是二选一

```python
if total_visible < need:              # 两种口径都不达标
    tier = 'BLOCK'
elif total_cjk < need <= total_visible:  # 平台口径达标，汉字口径不足
    tier = 'CONFIRM'                  # ← 人工在作者后台核对显示字数
else:
    tier = 'INFO'
```

理由：这里**确实存在真实歧义**（后台可能显示汉字数），
所以既不该硬判 BLOCK（挡住合法投稿），也不该硬判 INFO（可能让不足的稿子投出去）。
**降为 CONFIRM 并写明「投稿前必须在作者后台确认该书显示的字数」**是对的处置。

修后实测：逆袭书 **BLOCK 1 → BLOCK 0**，两个检查器结论一致；
`qimao_check --selftest` 仍 PASS。

### 新增夹具 `test_wordcount_caliber.py`（4 项）

汉字不足但平台口径够 → CONFIRM（不 BLOCK）／两种口径都不足 → BLOCK／
`--selftest` 仍通过／逆袭书 BLOCK 0 项。

### 这一条与第十八节是同一类缺陷

审计第十八节曾写过「同一概念两处口径：体检报告与判别力分析对不上」。
**这次是同一类缺陷的第二次出现**——两个模块各自算各自的字数，谁也不知道对方
判了什么。差别在于这次它有实际后果：**挡住投稿**。

4. **判别力门槛仍差 1 本样本。** `action_beat_per_1000` 的 verdict 仍是
   `UNVERIFIED_INSUFFICIENT_INDEPENDENCE`（拒稿样本 2 本，门槛 3 本）。
   第 1–8 章节拍密度落在真实拒稿样本区间内——该指标目前只能作定位线索。
5. **机械闸门全绿 ≠ 编辑会喜欢。** 已知反例《边镇小吏》：
   机械 BLOCK=0、fact_gate 全绿、跨章重复 0 条，仍被七猫拒，编辑原话
   「文笔在风格上不够统一、不够流畅、在细节刻画上力度稍弱」。

## 四十一、闸门把「接口约定」当「裁决内容」来判：三层根因与修法（2026-11-19）

### 现象

冷启动书《铁饭碗》跑到 N06（设定校验）卡死。judge 交上来的裁决**内容是对的**：
5 个维度全查了、风险都正确判成 A 级、引文是从 `设定/文风.md` 逐字抄的。
`done` 仍然以 `quote_check_failed: items 为空` 把它**整份判废**。

### 决定性实验：judge 到底读没读源文件

在动任何代码之前，先回答「是 judge 没干活，还是工具没认出来」——
这决定了该修提示词还是修工具。

做法：对 judge 写的 `detail` 散文，逐字滑窗找它与源文件的最长公共子串。

| 项 | 结果 |
|---|---|
| 角色.md | **命中 28 字**「把这台趴窝的老车床跑通，然后证明合同工也能在工艺卡上签字」 |
| 文风.md | **命中 14 字**「每个技术段落至少1个可核数字」 |
| 顶层 quote | **命中** `设定/文风.md` |
| 题材定位.md / 世界观.md | 0 字（这两项本来就是结构性检查，没有可引的句子） |

结论：**judge 确实读了源文件，它的引文是真的**。被判废的不是内容，是键名。

### 三层根因

| 层 | 状态 | 性质 |
|---|---|---|
| ① 提示词层 | 已修：所有 verify 节点自带完整 JSON 结构 | 措辞问题 |
| ② **归一化层** | **不存在** | **工具缺陷** |
| ③ **报错层** | 只说「items 为空」 | **工具缺陷** |

**② 归一化层缺失**——`_validate_judgment` 把键名（`items` / `criterion` /
`verdict` / `quote` / `source` / `level`）当成硬性要求。judge 只要把裁决项
写进 `checks`、键名用 `name`/`result`/`detail`，整份文件就被判废。
**被废掉的是「语义有效的工作」，丢掉的只是「接口约定」。**

**③ 报错层不自解释**——`quote_check_failed` 的载荷只有
`{"reason": "items 为空：judge 必须给出裁决项"}`。执行方看不到正确结构该长
什么样。对话路径又没有 P2 那样的自愈回路，于是同一份坏裁决反复重派。

### 修法

**② 归一化层**（新文件 `scripts/judgment_norm.py`）

- 别名容器/别名键 → canonical：`checks|findings|results` → `items`；
  `name|title` → `criterion`；`result|status` → `verdict`；
  `detail|basis|依据` → 散文池；`file|path` → `source`。
- 散文回捞：judge 没给引文但写了分析时，从散文里捞**真正逐字命中源文件**
  的连续片段补上。
- 引文命中但 source 写错 → 改指到真正命中的那个文件。
- **底线：只搬运，不造事实。** 回捞必须真的逐字命中；捞不到就如实报错，
  绝不替 judge 圆场。
- 质量门槛：回捞片段至少含 **12 个汉字**。`verify_quote` 的下限是
  「原始长度 ≥12 且归一后 ≥4 字符」，按这个下限会捞到
  「`、`设定/势力.md`），」这种路径碎片——逐字，但不是引文，拿它充数等于
  把「证明读过源文件」这条实质要求掏空。

**裁决契约重订**（提示词与校验器必须说同一件事）

引文的作用是给**阻断性结论**提供依据，不是给每条观察发证书：

- `items` 非空；顶层 verdict ∈ {pass, block}；block 至少有一项 fail；
- **fail 项必须给命中 source 的逐字引文**（修复指令要落到具体字句上，必须有据）；
- **pass 项可省引文**（结构性检查本来没有可引的句子，硬要引文只会逼 judge 编）；
- **整份裁决至少要有一条命中引文**，以证明 judge 真读了源文件；
- 机械项（有 `metric`）本身即是取证，豁免引文条数。

**③ 报错层自解释**：`quote_check_failed` 的载荷现在自带
`detail`（目标结构 + 字段规则 + 允许引用的文件清单 + 可直接抄的示例）、
`required_schema`、`allowed_sources`、`example`。示例是**自洽**的——
引文真的来自它标注的那个 source（随手拼一个执行方照抄必然被拒的范例，
比不给示例更糟）。

**④ 反馈回灌（新增）**：失败落盘 `state.last_failure`，下次
`autopilot.py next` 把它作为「【上一轮失败反馈】」拼到 `subagent_prompt`
前面——抬头与格式和 P2 无人值守路径（`server/agent/runtime.mjs`）完全一致。
此前只有 P2 有自愈回路，对话路径没有；现在两条路径行为一致。

### 证据

- 新夹具 `server/tests/test_judgment_normalize.py`：**29 项全过**
  （别名归一 / 散文回捞 / 路径碎片挡掉 / fail 无引文拒 / 零引文拒 /
  引文不命中拒 / source 越界拒 / block 无 fail 拒 / canonical 不被改写 /
  报错载荷自解释 / 失败落盘 / next 回灌 / 归一化落盘 / 成功后消费反馈）。
- 全量契约回归 `python_contracts.py` → **PY_CONTRACTS_OK**（18 项夹具）。
- 全部历史裁决文件逐份对拍：**旧校验器与新校验器结果完全一致**，
  唯一差异是冷启动 N06（旧 1 错 → 新 0 错）。**零回归。**

### 顺带查出来的两件事

1. **已封板章节的引文会失效。** 逆袭书/顶职的 `judgments_C*.N15.json` 里，
   部分 quote 在**当前正文里已经找不到**（也不在任何其他章节里）。
   原因是这些章在 N15 裁决之后又被改写，闸门的取证基准随正文漂移而失效。
   旧校验器同样拒——**不是本次引入的回归**，但它是真实存在的机制缺陷：
   闸门通过时的证据，与封板时留在磁盘上的正文，已经不是同一份文本。
2. **`qimao_check.py` 检不了真正的投稿物 —— 已修。** 此前它只接受章节目录，
   而编辑实际收到的是合并后的 `投稿包/全文.md`：**「投稿前检查器」检查的
   不是投稿的那份东西**。修法见下节。

## 四十二、补上投稿前检查器的最后一块：让它检得了真正的投稿物（2026-11-20）

### 缺口

`qimao_check.py --manuscript <书目录>` 从 `正文/` 逐章读稿。
但**编辑实际收到的是 `投稿包/全文.md`**——一份合并稿。工具因此出现一个
荒唐的错位：投稿前检查器检查的不是要投的那份文件。

更糟的是，把 `投稿包/` 目录直接喂给它会**更糟**：目录里有 `体检报告.md`、
`投稿邮件.md`、`投稿记录.md`，旧的「目录里所有 .md 都算正文」的兜底逻辑
会把体检报告的字数算进稿子里。

### 修法

`--manuscript` 现在接受三种输入，优先级固定：

1. 一个 `.md` 文件（合并稿）→ 按 `# 第NNN章` 标题切章后体检；
2. 书目录且含 `正文/` → 按章逐个体检（原有行为，优先级最高）；
3. 书目录且含 `投稿包/全文.md` → 体检真正的投稿物；
4. 其余目录 → 目录里所有 .md，但**排除** `体检报告/投稿邮件/投稿记录/全书概要/卷纲`
   这些非稿件文件。

### 关键约束：两条路径的口径必须逐字一致

合并稿的 `# 第NNN章 标题` 行**只在合并稿里存在**（`正文/第NNN章_*.md` 没有
标题行）。切分时若把标题行算进正文，合并稿口径就会比逐章口径每章多出
约 10 字——于是「用哪份稿子体检」会改变结论，检查器成了薛定谔的检查器。
因此切分时**标题行只作分隔符，不进正文**。

实测（逆袭书 9 章）：逐章路径与合并稿路径给出**完全相同**的数字——
`9 章 / 17734 汉字 / 可见字符 20903`。回归夹具已把这条钉住
（`test_wordcount_caliber.py` 扩到 6 项：新增「合并稿与逐章口径一致」
与「书目录自动走正文，不混入体检报告等非稿件」）。

## 四十三、过期绿灯：闸门说「这章审过了」，而它依据的原文已经不存在（2026-11-20）

### 现象

逐章对拍历史裁决文件时发现：逆袭书 C1/C3/C6 与顶职 C1/C3 的章级裁决里，
**共 10 条引文在当前正文里找不到了**。失配原因是正文被微改过：

```
旧裁决引的：翠芬婶看他不说话，又添了一句。
当前正文是：翠芬婶看他不说话，又添一句。
旧裁决引的：爹半年前工亡，留下一个顶职名额，还有那笔没发下来的抚恤金。
当前正文是：爹快两年前工亡，……还有那笔没到手的抚恤金。
```

### 为什么漂移检测没有抓到它

`_body_post_commit_drift`（2026-11-17 加）比对的是「账本记的 `body_sha256`
vs 磁盘现状」。而 **revision 定稿会把正文和账本 sha 一起更新**——账本与磁盘
完全一致，检测结论是「一致，没被篡改」。

漂移检测盯的是「**被篡改**」，盯不住「**被合法修订但没重裁**」。
于是那份裁决的节点状态仍写着 done：一份**过期绿灯**。

这比篡改更危险：篡改会被报出来，过期绿灯**看起来一切正常**——
闸门说「这章审过了」，而它依据的原文已经不存在。

### 修法三件套

**① 检测** —— 新增 `inline_runner._stale_gate_evidence(book, chapter)`：
逐条验证裁决引文是否仍命中它标注的那个源文件。失效即报（章号 / 判据 /
引文 / 原因）。

**② 阻断** —— N21 打包时逐章扫一遍，**任何一章的裁决依据过期 → 判不可投**
（`NOT_SUBMITTABLE`），体检报告第五节写明是哪几章哪几条引文，
并给出修法。revision 定稿时也立刻警告，避免问题一路带到打包才发现。

**③ 补救** —— 新增 `autopilot.py rejudge --book <书> --chapter N`：
**带外重判**该章的裁决闸门。

- 为什么必须带外：流水线是线性的，游标一动就会重跑后面所有章；
  常规 `C{n}.N15` 的 block 还会把游标拨回 `C{n}.N14` 去改写正文——
  对一本**已完稿**的书，那是把它重新拉回写作链。
- 因此 `rejudge` 单独为 `C{n}.N15` 签一枚令牌，judge 重写裁决文件，
  `done` 接受它但**不动游标**；若重审判 block，如实报出
  （`rejudge_blocked`）并要求先改正文再重判，同样不回退。

### 证据

- 新夹具 `server/tests/test_stale_gate.py`：**15 项全过**
  （命中/失效/检出/rejudge 签发/不动游标/done 接受/过期清零/
  block 报错且不回退）。
- 全量契约回归 → **PY_CONTRACTS_OK**（19 项夹具）。
- 逆袭书 C1.N15 已用该回路**真实重判过一次**（旧裁决 2 条引文失配）。

### 这条机制的意义

它把「闸门通过」这句话的含义收紧了：不是「某个时刻有人审过」，
而是「**现在这份正文**有人审过，且审的依据仍然成立」。
这正是「取证基准」概念在闸门侧的落点——此前只有日链、伏笔、字数这些
**数据基准**被校准过，**裁决基准**一直没人管。

### 重判当场查出真问题（这条机制的实证价值）

《逆袭从掌控系统开始》C6.N15 带外重判，judge 判 **block**，5 条 B 级硬伤：

| 判据 | 缺陷 |
|---|---|
| 因果链 | 开篇写「铁片划出新鲜亮痕」（撬锁），后文陆明却断言「他拿的是我家那把钥匙」——两种开门方式互斥 |
| 人物一致性 | 刚对翠芬婶隐瞒遭窃，下一句当面自曝「前天夜里开门的就是他」，再下一句又写「翠芬婶看他不说话」 |
| 实物闭环 | 系统说「技术笔记已接入」，但本章只拆出半张抚恤凭据，**没有工票与烟盒硬纸板**——系统读的东西在现场不存在 |
| 前后打架 | 中段「把门轴上的灰照原样补了一层」，章末却写「只有门轴上那道痕还在」 |
| 流水账 | 前文明写陆明没动过木箱/棉袄/床板/灶台砖，结尾却逐项把它们「照原样」重新摆弄一遍 |

这五条**全在旧裁决通过之后、正文被修订之后才成立**——旧裁决判 pass 时，
它们中的大部分还看不出来。也就是说：**那份过期绿灯掩盖了真问题**。
闸门不是"坏在没审"，是坏在"审的是另一份文本"。

修法生效：重判判 block 时，工具**如实报出 5 条 fail + 各自 fix，
且流水线游标一动不动**（`cursor` 仍为 `__done__`）——
没有把已完稿的书重新拉回写作链。修完正文再跑一次 rejudge 即可。

## 四十四、自动裁剪是死代码：写进审计的能力从未跑起来过（2026-11-20）

### 现象

冷启动书第 1 章正文 2695 可见字（上限 2600），N12 预检判 `LENGTH_OVER`
打回。理论上工具应该**自动裁到带内**——`_text_preflight` 里有一段
2026-11-17 加的自动裁剪，注释写着「超长章此前只会被判 over 并打回，
由人逐段读、逐段删——第 2 章手工裁 689 字」。

但它一次也没跑过。

### 根因：两个 import 错误 + 一个裸 except

```python
try:
    from inline_runner import trim_to_band, CHAPTER_BODY_MAX_CHARS   # ① 抛 ImportError
    from wordcount_core import count_visible_chars                  # ② 模块不在 sys.path
    ...
except Exception:
    trim_notes = []          # ③ 吞掉，不说一个字
```

① `CHAPTER_BODY_MAX_CHARS` 定义在 `pipeline_spec`，不在 `inline_runner`；
② `wordcount_core`（平台字数口径的**唯一实现**）只存在于 story-long-write
技能的 scripts 目录里，工作台从没把它挂到 `sys.path`；
③ 裸 `except Exception` 把两个错吞成「没什么可裁」。

**这是同一类病的第三次出现**：`IndexError` 被吞成「无问题」、
`except Exception` 把「工具坏了」和「没发现问题」混为一谈。
区别只是这次吞掉的不是检测结果，而是一条**本该自动完成的动作**。

### 修法

- 常量从 `pipeline_spec` 导入；
- 新增 `inline_runner.visible_chars()`：按 config 里的 `STORY_LONG_WRITE`
  **挂技能 scripts 目录**再 import——**只挂路径，不抄实现**（抄一份就会
  和技能漂移，那正是这套工具反复吃的亏）；
- 技能路径改成**多候选**（config 指向 + 用户目录标准位置），
  避免 config 指向失效目录时整个字数口径取不到；
- 取不到时抛**带排查线索**的 RuntimeError（列出试过的目录），
  不再静默；
- 裁剪失败写进返回载荷的 `auto_trim_error`，不再吞。

### 证据

- 修前：2695 → 2695（裁剪一次没跑）。
- 修后：2695 → **2561**（删 4 段，落在 2000–2600 带内）。
- 新夹具 `server/tests/test_auto_trim.py`（6 项）：口径可用 / import 不再抛 /
  真的裁到带内 / 确实删了内容 / 有可读说明 / 开场段与末段（钩子）受保护。
- 该夹具在**假 config**（`STORY_LONG_WRITE` 指向空目录）下也必须过——
  这正是它第一次失败的原因，也是多候选路径解析的由来。

## 四十五、四条新修的机制缺陷（2026-11-20，冷启动书第 6–7 章实跑逼出来的）

前四十三节修的是「闸门认不出有效的裁决」。这一节修的是**跑起来之后才暴露的、
机制内部自相矛盾**的四条——它们都不是提示词问题，都是代码问题。

### 1. 文件所有权冲突：工作台抢了技能的文件

`追踪/上下文.md` 是 **tracking_commit.py 自己从 `_tracking-state.json` 派生的
权威视图**（它的 `check` 子命令逐字节比对，任何偏离都报
「derived view differs」）。而工作台的 N11 节点把 S1–S7 的 writer 上下文
**写进同一个文件**——等于抢了技能的所有权。

后果：每次封板后技能把它覆写回自己的格式，于是
`tracking_commit.py check` 对工作台的书**永远报不一致**（假警报）；
书一旦崩在章间，运维拿这个命令根本诊断不了账本。

修法：**各写各的文件**。技能管 `上下文.md`（派生视图），工作台管
`追踪/写作上下文.md`（场景卡/上一章锚点/事务说明）。N11 的产物路径、
N12 提示词的读取路径、`_context_md_intact` 守卫的检查对象，三处一起改。

### 2. 带外重判被漂移检测拦死

`_body_post_commit_drift` 比对「账本记的 body_sha256 vs 磁盘」。
带外重判（`rejudge`）的用途**就是**重判被改过的章——目标章的正文**必然**
与账本不一致。不豁免的话，最自然的顺序「改正文 → 重判 → 提交」会被拦死，
逼人先走一遍 revision 重新封板，白费一轮。

修法：漂移检测加 `exempt_chapter` 参数——**只豁免正在重判的那一章**，
别的章照拦。

### 3. 退役声明被压缩器截断，报错信息与真实原因对不上

第 6 章 writer 明明在 `delta.retired_context_items` 里声明了被删的
context 条目，`done` 仍报：

```
context items were dropped without being declared in delta.retired_context_items:
三号床精度攻关刚开刀，圆度病灶拆成床子与炉子两处，扭曲量与淬火余量都还没数出来。
```

writer 明明写了。真因是**工作台的规整器把声明截到 30 字**（为把体积压到
3072 字节），而工具做的是**精确集合比对**——截断一个字就匹配不上。
更深一层是**两处口径不一致**：预检的体积检查**排除**
`retired_context_items`，压缩器的口径**包含**它 → 同一份事务两套口径 →
压缩被触发 → 截断 → 声明失效。

修法：① 压缩器口径与预检对齐（都排除）；② 退役声明**不截断**
（工具提交时会按账本用 `sorted(dropped)` 重新生成）；③ 规整器顺手**还原**
历史上被截断过的声明（前缀命中即认定为截断）。

**这一条的教训比前两条更值钱**：报错信息把执行方引向「再写一遍」，
而再写一遍还会被截断——**死循环**，而且每一轮都烧掉一个 LLM 节点。
**报错信息必须能指到真实原因**，否则它比没有报错更糟。

### 4. 契约里两条规则数学上互斥

写作契约同一页上写了两条打架的规则：
「收尾带因果词的段落应 **60%–85%**」与「因果密度 **≤6.0/千字**」。

算术：闸门按 16 词的 `CAUSAL` 词表算密度；生死线「段/千字 33–54」意味着
2200 字的稿子有 73–119 段；6.0/千字 × 2.2 = **全章最多 13 个**计分因果词；
而 60% 的 73 段 = **44 段**要带因果词 → 需要 44 个词，上限只给 13 个。

后果实测到了：一个 writer 直接向编排者报告「这两条规则互斥」；
另一个只好用**闸门不统计**的词（反倒/到底/毕竟）凑收尾率——收尾率达标了，
但那些词根本不在 `CAUSAL` 词表里，等于**用漏洞而不是用规则**。

修法：以**标定过的密度区间**为准（1.0–6.0/千字，14 本签约书，不能改），
收尾率改成算得通的 **1/4–1/3**，并把算术写进契约与 N12 提示词。
新夹具 `test_causal_contract.py` 会**自己算一遍**并断言
「契约写下的目标 ≤ 算出来的上限」——以后谁再写死一个数，它当场挂掉。
