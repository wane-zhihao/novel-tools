## 二、按严重度排序的发现

### A 级——动到信任假设，不修则上层建筑虚

**A1. step_token 的"100% 机械隔离"名不副实** ✅ **已被真攻击测试实证推翻（2026-10-24 02:0x）**
机制只校验"调用方是否持有正确 token"。但 token 明文存在 `_pipeline/state.json`，subagent 是 general-purpose 全工具权限，prompt 里"只给具体文件路径"是**提示词层面的约定，不是强制**。方案风险 2 承认此残留，但我的记忆与汇报写成了"100% 机械拦截"。
**实测（攻击书 `_phase0/attack_book`，授权渗透测试）**：
1. 盲调（无令牌，token=000000）→ exit 2 `token_mismatch`，拦截生效；
2. attacker 读 `_pipeline/state.json` → `step_token`/`step_token_node` **明文可读**；
3. 持真令牌调 done（自建 700 字占位 evidence）→ **exit 0，ok:true，N03 被标记 done，游标 N03→N04**；
4. 附加发现：llm 节点的 evidence 校验只是"文件存在+大小达标"，攻击者可自建占位文件通过——即被劫持的 agent 不仅能越权，还能**伪造完成痕迹**。
结论：token 只防"无意/无 token 调用"；对任何能读 state.json 的 agent（我们的 subagent 全都能）完全失效。OWASP 2025 将 prompt injection 列为 LLM 应用头号风险，而我们的 subagent 每轮都在读取**不可信内容**（小说正文、平台文档）——注入面真实存在，被劫持的 subagent 读到 state.json 即可获得合法 token。
→ 修复方向：token 移出 state.json（独立文件/环境变量，仅主会话可见，subagent prompt 不给路径）；或给 subagent 换受限工具面；或 done 增加调用方身份绑定。本次测试的攻击书保留在 `_phase0/attack_book/` 作为证据。

**A2. "无人值守"实证为零，且架构风险敞口大于同类方案**
本次联试证明的是"状态机力学正确 + 人工驾驶下各节点可过"，不是"无人值守可行"。Phase 0 只测了 6 轮。横向比对 novel-writer-cli（DankerMu）：它把**编排完全移出 LLM**——CLI 确定性计算 next/生成 instruction packet JSON/校验推进/事务提交，LLM 只当执行器。我们的编排在 LLM 主会话里，靠铁律+Rule Echo+检查点接力兜底——这是敞口完全不同的两种架构。联试中三次 blocked（闸门工具崩、事务 schema 违规、内容拦截）**全部依靠我（人类级推理）诊断恢复**，没有任何自动恢复发生。按 OrchestraBench 对多代理编排失败模式的分类，我们的"recovery"能力目前是外包给运气的。
→ 这不否定当前路线（宿主无 hook 是既定约束），但"完全无人值守"的验收项在当前证据下不应打勾。

**A3. judge 层未经校准，L1 准备给未经校准的裁判加权重**
外部文献（arXiv 2410.21819 等）证实 LLM judge 存在 self-preference bias（同族模型互评系统性偏高）、位置/长度偏见、估计有偏。我们的缓解（judge 隔离写作过程、红队 prompt、quote 硬校验）只治"编造引用"，不治"偏见"。联试 n≈6，两次 block 核验为真——但这是小样本巧合还是稳定能力，无数据。L1 九维权重（beat .25 等）是**未经校准的先验**，直接上线等于把偏见固化进结构。

### B 级——工程正确性，记录在案待修

**B1. N16 的完成方式是脏的。** tracking_commit 已 append 成功（revision 0→1）后，我把事务改 revision 模式让 storyctl 接管余下半场。功能完整但第 1 章追踪状态带着"先 append 后 revision"的补丁痕迹（revision=2）。根因是 N16 适配器误读上游契约（双调必炸）——适配器已修，但 book2 的状态不干净，且**第 2 章 draft 对 revision=2 的行为未验证**。

**B2. 我以 orchestrator 身份做了 writer 的活。** tracking.json 的语义压缩（character_changes 富结构→单句）由我执行，信息有损，角色分离被我自己破坏。正确路径是打回 writer。此事不重演比补救重要。

**B3. N08 回退预算被我单方面扩大。** 方案写"回 N07 ≤2 次"，实际打了四轮（r2/r3/r3b/r4）。我当时的裁定（"闸门指定的文书级修补不算实质性返工"）本身合理，但它是**运行中的单方面扩容，无事前批准**。联试暴露：预算规则需要定义"什么算一轮"，否则预算形同虚设。

**B4. subagent 自报指标系统性不可信（有双向实证）。** 我的联试：writer 自报数字密度 2.23/千字，自述证据（两处/2386 字）算术上就只有 0.84，闸门实测 0.0（口径只算阿拉伯数字）。并行会话：subagent 自报"已前移"实际差 21 字。**结论：一切自报数字必须过机器，一切"已按指令改好"的声称必须复测。** 我在 N13 做了闸门复测（好），但 N15 judge 的 summary 论断未独立核验（quote 校验只保证引用真实，不保证论断正确）。

**B5. words_total 永不更新（审计已知，联试再确认）。** target_words 停止条件死掉，只能靠 max_chapters。直接影响"保底 2 万字"验收项。

**B6. 闸门无反向测试集。** ✅ **已补（2026-10-24 02:0x，判别力证实）**
阳性对照实测（`gate_runner --genre niandai`）：
| 章节 | 已知状态 | 实测 |
|---|---|---|
| w1 v1 | 因果 11.07 + 动作词 46.53 双超 | **[BLOCK] exit=1**（G8/G9 双报），经 N13 包装器传播为 `status: blocked` ✓ |
| w1 v2 | 段/千字 60.2、句长 10 双偏 | [WARN] exit=0（G2-a/G3-a 按设计仅 advisory） |
| w1 v3 | 全绿 | [PASS] exit=0 ✓ |
| book2 现章 | 全绿 | [PASS] exit=0 ✓（我的 gate_runner 修复后无回归） |
结论：G8/G9 的牙齿真实（坏章 BLOCK 且退出码正确传播），好章不误杀。测试中更正了我自己的一个手法错误（管道后 `$?` 取的是 tail 的退出码）。残留：段密度/句长仅 advisory，w1 v2 这类"偏科章"只 WARN 不 BLOCK——是数据驱动设计（并集区间同题材无区分力），但意味着 N14 对这两项的收敛目标是软目标。另记：w1 因同章 4 个版本文件触发 storyctl"必须唯一文件"错——流水线原地覆盖不存在此问题，但 N14 若产出多版本文件会炸 N13/N16，属设计约束。

### C 级——流程卫生

**C1. 并行会话零并发纪律。** 两会话同一工作树，对方两次将我未提交的修改卷入其提交（我的修复被归进他们的 commit message）；git 归因已乱。novel-writer-cli 有 `.novel.lock/` 写入锁——我们没有任何锁或分工约定。
**C2. gate_runner.py 的修复在版本控制之外。** F:\小说\ 侧不受 git 管辖；我与并行会话先后改了同一文件（我修 note-key 崩溃，他们修 genre 区间/双向边界/指标映射），现文件含双方改动，无版本、无测试。平台工具层在裸奔。
**C3. 汇报的选择性呈现。** 我的结案汇报强调"闭环达成"，对"N16 是 revision 补完/N08 超预算/C2+ 未测/judge 未校准"着墨偏少。审计型读者会从 git log 挖出来——主动披露优于被挖。
**C4. 我呈给用户的第 1 章，我自己没读过。** 闸门只验机械指标；judge 说 pass 但 judge 未校准（A3）。用户看到的"全关卡通过"文本，文学质量无人背书——这不违规（禁读铁律），但呈现时应该说清"机器通过 ≠ 写得好"。

## 四、结论

**扎实的部分**：审计找出的问题全部真实；P0/集成修复经编译+自检+实跑三重验证；联试中闸门真实拦截了真实问题（AI 句式+字数），拦截→改写→复过的回路是通的；追踪事务 schema 的严苛性被完整测绘。这些是工程事实，不含水分。

**不扎实的部分**：项目的第一卖家（完全无人值守）实证为零；三个信任假设（token 安全、judge 可靠、orchestrator 纪律）都只有间接证据，其中两个（A1/A3）有直接的反证材料；L1 若在 A1–A3 修复前上线，是把未经校准的裁判制度化。

**一句话**：我们把"管道"修通了，但还没证明"石油"能自动流过去——而 L1 是在给还没质检过的流量计加权。

## 五、选项

- **A（推荐）**：先花一轮补三个高杠杆验证——① 真攻击测试（派 subagent 尝试读 state.json 调 done，实测 token 边界）② 闸门反向测试集（拿被拒稿章节+已知坏章节当阳性对照，验判别力）③ C2 试跑一章（验 revision=2 与循环可重复性）。三项全过再上 L1，L1 的地基才实。
- **B**：按原批准顺序直接上 L1，A1–A3 记录在案延后。代价：权重先于校准固化，A1 的安全高估继续挂着。
- **C**：认真评估 novel-writer-cli 式"确定性编排 CLI + instruction packet"迁移（最大赌注：编排移出 LLM 后，无人值守从"纪律问题"变成"工程问题"）。建议单开一轮调研，不动手。

我的建议是 A：三项验证各约 20–40 分钟，全部是"用证据换掉假设"，正好接在 L1 前面；B 是带病上岗，C 的赌注应该在 A 的证据出来之后再评估。
